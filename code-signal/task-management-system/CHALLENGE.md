# Task Management System: CRUD, Search, Quotas, Expiring Assignments

Implement an in-memory task management system that grows over four levels. Each level adds requirements on top of the previous ones, and everything from earlier levels must keep working, so the design choices made in Level 1 decide how painful the later levels are. As reported, this is a standard CodeSignal Industry Coding Assessment: one class, four cumulative levels, screen-share and mic on for the whole session.

The exact method names and signatures were not reported — only the level descriptions below. Work from an interface like the illustrative one that follows, and settle the open points with the clarifying questions under each part. Timestamps are assumed to be integers passed as the first argument to every operation, the same convention CodeSignal uses in its other "system" problems (banking, parking lots, etc.), because Level 3's automatic expiry needs a clock.

```py
class TaskManagementSystem:
    def add_task(self, timestamp: int, task_id: str, title: str, description: str, priority: int) -> bool: ...
    def update_task(self, timestamp: int, task_id: str, title: str, description: str, priority: int) -> bool: ...
    def get_task(self, timestamp: int, task_id: str) -> dict | None: ...
```

## Clarifying Questions
- Are task ids and user ids assigned by the caller (as in the signature above) or generated by the system and returned?
- Is `update_task` a full overwrite of title/description/priority, or a partial update where omitted fields are left alone?
- Are priorities small integers where a larger number means more urgent, and can two tasks share a priority?

## Part 1 — Basic task operations
Support adding, updating and retrieving tasks.

### Clarifying Questions for this Part
- Does adding a task with an id that already exists fail outright, or overwrite?
- Does updating or retrieving an unknown task id return `False`/`None`, or raise?
- What fields does a task have beyond title, description and priority — created-at timestamp, status?

### What This Part Should Cover
- Task storage keyed by id, with duplicate-id and unknown-id handling stated up front.
- A task representation that has room to carry assignment and completion state later without a rewrite.
- Consistent, documented return values for success and every failure case.

## Part 2 — Search and listing by priority
Add:
```
search_tasks(timestamp, keyword)
list_tasks(timestamp)
```
`search_tasks` finds tasks whose name/title contains the keyword. `list_tasks` returns tasks ordered by priority.

### Clarifying Questions for this Part
- Is the keyword match case-insensitive, substring, or does it also search the description?
- Does priority sort descending (most urgent first) or ascending, and what breaks a tie between equal priorities?
- Do both operations return full task objects, just ids, or something else?

### What This Part Should Cover
- A precise match rule for search and a deterministic sort with an explicit tie-breaker for listing.
- Whether these are computed at query time or maintained incrementally as tasks change.

## Part 3 — Users, quotas and expiring assignments
Add:
```
add_user(timestamp, user_id, quota)
assign_task(timestamp, task_id, user_id, duration)
```
A user has a quota: the maximum number of assignments they can hold at once. A task itself carries no assignment state — it can be assigned to the same user more than once, or to several different users, all at the same time. Each call to `assign_task` creates its own independent assignment with its own lifetime (`duration`); once that time elapses without that specific assignment being completed, it expires automatically. Completing or expiring one assignment never touches any other, even one for the same task and the same user.

Because a task can have several outstanding assignments at once, `assign_task` returns an identifier for the one it just created — the same shape as `schedule_payment`/`payment_id` in the banking variant of this series — so a later operation can refer to that exact assignment instead of guessing which one among several.

This identifier aside, expiry is the hinge of the whole problem, the same shape as CodeSignal's scheduled-payment and expiring-reservation variants: nothing calls an "expire" method. From the moment an assignment exists, every subsequent operation — whatever it is — may first have to expire assignments that became due before its timestamp, and only then do its own work. A quota count or a listing computed without that sweep sees stale state.

### Clarifying Questions for this Part
- Confirming: is there no limit on how many independent assignments a single task can have outstanding, as long as each assignee has quota for it?
- Does an expired assignment free only that assignment's slot in its user's quota, leaving every other assignment (for that task or that user) untouched?
- Is expiry checked against every outstanding assignment, every time, or only those touching the user/task an operation names?
- Is `duration` relative to the assignment's own timestamp (`due_time = timestamp + duration`), and is `due_time` inclusive — does an operation stamped exactly at `due_time` see the assignment already expired?

### What This Part Should Cover
- A data model where the assignment, not the task, is the unit of state — keyed by its own id, not by (task_id, user_id).
- A single place where time advances and due assignments expire, run before every operation, touching only the expiring records.
- Quota accounting that is always correct after an expiry, not just after an explicit completion.

## Part 4 — Completing assignments and reporting overdue ones
Add:
```
complete_task(timestamp, assignment_id, user_id)
get_overdue_assignments(timestamp)
```
`complete_task` finishes one specific active assignment, identified by the id `assign_task` returned. `get_overdue_assignments` reports assignments that passed their due time without being completed.

### Clarifying Questions for this Part
- Does completing a task require the caller to be the specific user that assignment was made to, and what happens if that exact assignment already expired (even if other assignments for the same task/user are still active)?
- Is "overdue" exactly the same set as "expired" from Part 3, kept as history instead of being discarded, or is there a separate grace window between due and overdue?
- What does `get_overdue_assignments` return — assignment ids alone, or (assignment, task, user, due_time) tuples — and in what order, given several entries can share a task or a user?
- Once reported, does an overdue assignment ever leave the report, or does it stay forever as history?

### What This Part Should Cover
- Reusing the Part 3 sweep as the single source of truth, rather than a second, independent notion of "late."
- A decision for the race between `complete_task` and the sweep at the same timestamp, stated explicitly.
- Deterministic ordering for the overdue report when multiple entries share a task or a user.

## What a Strong Answer Covers
- A data model chosen in Level 1 that survives Levels 2 to 4 without a rewrite (tasks, users and assignments as separate, linked records).
- One sweep function that expires due assignments, called at the top of every public method, exactly like the scheduled-payment problems in this series.
- Deterministic behavior: tie-breaks, expiry semantics and return values stated up front, not improvised mid-interview.
- Failure paths that leave state unchanged, with a test per level exercising the success and failure cases.
- The time complexity of each operation, and what changes if assignments number in the millions.

## Follow-up Questions
- How would you answer "how many tasks has this user completed, and how many did they let expire?"
- If `assign_task` could be called concurrently for the same task by two callers, what would break and how would you fix it?
- If `get_overdue_assignments` is polled every second while assignments rarely change, what structure keeps it fast?
- How would you extend this to recurring tasks, or to tasks with sub-tasks/dependencies?
